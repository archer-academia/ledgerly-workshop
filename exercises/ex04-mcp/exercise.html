MCP: current docs upstream, a gate downstream

Objective

Agents write code against the APIs they were trained on, and your lockfile is newer than their training data. The result passes every test and uses an API the library already deprecated. Watch that happen on a real Ledgerly ticket, connect Context7 so the agent can read the docs for the versions you run, add the rule that makes it look, and then make deprecated APIs a failing test, so the finish line from Ex 3 enforces it.

See outdated-library drift: working code, green tests, a deprecated API.

Add an MCP server at project scope with .mcp.json, and verify with /mcp.

Pair a capability with a rule that says when to use it.

Enforce downstream: warnings as errors for code you own.

Connect Context7: current docs, on demand

4 min

Add the Context7 MCP server at project scope, so the whole team gets it through git. Then check it's connected and what it costs.

▶ Create ledgerly/.mcp.json

{ "mcpServers": { "context7": { "type": "http", "url": "https://mcp.context7.com/mcp" } } }

▶ Check it in a fresh session

cd ledgerly && claude # approve the project server when asked # /mcp → context7 · connected · 2 tools # /context → note the MCP tools line

WhyMCP adds tools, not instructions: resolve-library-id finds the library, query-docs returns docs for the version you ask about. Every tool's schema loads into every session (Context slide: one uncurated server can cost more than the whole conversation). Project scope (.mcp.json) travels with the repo; user scope (claude mcp add --scope user) is just you, the same trap as Ex 1 Step 6.

Acceptance criteria
/mcp shows context7 · connected.
You wrote down the MCP tools token count from /context.
Stuck? Hints unlock in order
1 · nudgeIt asks to approve the server
Project-scoped servers need a one-time approval per user: that's a security feature, not an error.
2 · specificRate-limited?
Context7 works without a key; a free key raises the limits. Add a header to the server entry, reading the key from your environment:
"headers": { "Authorization": "Bearer ${CONTEXT7_API_KEY}" }
3 · near-completeNo network for HTTP servers?
Use the local stdio server instead:
"context7": { "command": "npx", "args": ["-y", "@upstash/context7-mcp"] }

Tell the agent when to use it

5 min · red → green

A connected tool the agent never calls changes nothing. Add a rule that says when to consult it, then rerun the same ticket.

▶ ledgerly/.claude/rules/libraries.md

# Third-party library APIs - Training data is older than our lockfile. Before writing code against a library API (FastAPI, Pydantic, Starlette, pytest), look it up with the **context7** MCP server: `resolve-library-id`, then `query-docs` for the version pinned in `uv.lock`. - Prefer the current API even when the deprecated one still works. Deprecated today means removed in the next upgrade (e.g. FastAPI `lifespan`, not `@app.on_event`; Pydantic `field_validator`, not `@validator`).

▶ Same ticket, fresh session

tools/start.sh led-141 && cd ledgerly && claude # paste LED-141, /exit cd .. && tools/check.sh led-141

PASS no-deprecated-apis no deprecated APIs in Ledgerly's code PASS looked-up-current-docs => GREEN

WhyThis is Ex 1–2 again: MCP is a capability, the rule is the instruction that makes the agent reach for it. It's still advisory: you get a rate. That's why Step 3 exists.

Acceptance criteria
tools/check.sh led-141 → GREEN: the transcript shows mcp__context7__… calls and the code uses lifespan.
Stuck? Hints unlock in order
1 · nudgeIt didn't call context7
Did the rule load? /context should list .claude/rules/libraries.md. Or say "use context7" in the prompt once to see the tool work.
2 · specificlooked-up passes but deprecated fails

Make it enforced, not just likely

4 min

Turn "don't use deprecated APIs" into a test failure for Ledgerly's own code. This edits pyproject.toml, which your Ex 3 fence routes to a human: you make this change, not the agent.

▶ 1 · Put the deprecated version in place

tools/demo_reference.sh led-141 red # resets ledgerly/, applies the on_event code uv --directory ledgerly run pytest -q # still green: that's the problem

▶ 2 · Add one line under [tool.pytest.ini_options] in ledgerly/pyproject.toml

filterwarnings = ["error::DeprecationWarning:ledgerly"]

▶ 3 · Prove it bites

uv --directory ledgerly run pytest -q # now FAILS: on_event is deprecated…

WhyMCP fixes it upstream (better knowledge, advisory). The warning filter fixes it downstream (a gate, deterministic), and your Ex 3 finish line now refuses "done" on it automatically. The :ledgerly part limits it to warnings raised from our modules, so a library's own internals can't break the build.

Acceptance criteria
Before the line: pytest green on deprecated code. After it: fails on the on_event line.
tools/reset.sh --keep-memory afterwards puts the code and pyproject.toml back. In your own repos, commit the line.
Stuck? Hints unlock in order
1 · nudgepytest still passes
The line must sit inside the [tool.pytest.ini_options] table, next to addopts, not at the end of the file under another table.
2 · specificWhy not `error::DeprecationWarning` for everything?
A dependency's internal warning would break your build on an upgrade you didn't make. Scope the gate to the code you own.
3 · near-completeShouldn't the agent add this?
It's a team decision about the build, and the fence asks a human on purpose. That's Ex 3 working.
